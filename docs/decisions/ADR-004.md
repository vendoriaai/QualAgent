# ADR-004: Project registry for multi-project discovery

## Status

Accepted (2026-08-18)

## Context

TAD/roadmap place one SQLite database per study directory
(`{study}/.qualagent/qualagent.db`), yet the API surface requires listing
projects across the machine (REST `GET /projects`, MCP `list_projects`), and
04_DATA_MODEL marks project names unique. Nothing in the specs defines how
projects are discovered.

## Options

1. **Single global DB holding all projects.** Contradicts per-project DB in
   roadmap 1.2 and couples studies together.
2. **Registry file mapping project id -> study path.** Per-project DBs stay
   independent; a small JSON registry at `~/.qualagent/registry.json` enables
   listing and lookup.

## Decision

Option 2: each study keeps its own DB and `.qualagent` directory; a machine
level registry (`~/.qualagent/registry.json`, overridable via
`QUALAGENT_HOME`) records `{project_id: {"name", "path", "created_at"}}` on
`init` and is the source of truth for cross-project listing. Deleting a
project removes its registry entry (audit event written first).

## Consequences

- Studies remain portable (copy a study directory = copy the project).
- REST/MCP servers resolve `project_id` -> path via the registry; when started
  with an explicit `--project-dir`, that single project is used directly.
- Registry corruption only affects discovery, never project data.
